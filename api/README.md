# WaterBonia API Documentation

REST API for ESP32 device communication with the WaterBonia server.

**Base URL:** `http://localhost/WaterBonia/api/`
**Content-Type:** `application/json`

---

## Authentication

ESP32 devices authenticate using **Bearer tokens** passed in the `Authorization` header.

```
Authorization: Bearer <DEVICE_TOKEN>
```

- Tokens are **generated by admins** via the Devices web page.
- Tokens are stored as **SHA-256 hashes** in the database.
- Raw tokens are **shown only once** at generation time.
- Never put tokens in query strings, URLs, or logs.

## Endpoints

### GET /api/status

Public endpoint. Returns API status and available endpoints.

**Response (200):**
```json
{
  "success": true,
  "data": {
    "system": "WaterBonia",
    "version": "0.1.0-dev",
    "api_version": "1.0.0",
    "timestamp": "2026-09-21T10:00:00+08:00",
    "endpoints": { ... }
  }
}
```

### POST /api/device/heartbeat

Device heartbeat. Updates device status, IP, firmware, and Wi-Fi info.

**Headers:** `Authorization: Bearer <token>`, `Content-Type: application/json`

**Request:**
```json
{
  "firmware_version": "0.1.0",
  "ip_address": "192.168.1.10",
  "wifi_ssid": "MyWiFi"
}
```

**Response (200):**
```json
{
  "success": true,
  "data": {
    "device_id": 1,
    "status": "online",
    "timestamp": "2026-09-21T10:00:00+08:00"
  },
  "message": "Heartbeat accepted."
}
```

**Behavior:**
- Updates `devices.last_seen_at`
- Updates `firmware_version`, `ip_address`, `wifi_ssid` if supplied
- Sets device status to `online` if previously `offline` or `maintenance`
- Logs `device_connected` when device comes online
- Rate limit: 30 requests per 60 seconds

---

### POST /api/device/sensor-reading

Receives sensor telemetry from the ESP32.

**Headers:** `Authorization: Bearer <token>`, `Content-Type: application/json`

**Request:**
```json
{
  "water_level_percent": 72,
  "cup_detected": false,
  "hand_detected": false,
  "pump_status": false,
  "battery_percent": 84
}
```

**Response (200):**
```json
{
  "success": true,
  "data": {
    "reading_id": 123,
    "recorded_at": "2026-09-21T10:00:00+08:00"
  },
  "message": "Sensor reading accepted."
}
```

**Validation:**
| Field | Rules |
|-------|-------|
| `water_level_percent` | 0–100 or null |
| `battery_percent` | 0–100 or null |
| `cup_detected` | boolean |
| `hand_detected` | boolean |
| `pump_status` | boolean |

**Behavior:**
- Stores reading in `sensor_readings`
- Updates `devices.last_seen_at`
- Checks low-water threshold and creates/resolves alerts automatically
- Rate limit: 60 requests per 60 seconds

**Low-Water Alert Logic:**
- If `water_level_percent <= low_water_threshold` and no active `low_water` alert exists → creates alert
- If `water_level_percent > low_water_threshold` and active `low_water` alert exists → auto-resolves it
- No duplicate alerts while water remains below threshold

### POST /api/device/dispensing/start

Starts a new dispensing session.

**Headers:** `Authorization: Bearer <token>`, `Content-Type: application/json`

**Request:**
```json
{
  "cup_detected": true,
  "hand_detected": true,
  "water_level_before": 72
}
```

**Response (201):**
```json
{
  "success": true,
  "data": {
    "session_id": 456,
    "started_at": "2026-09-21T10:00:00+08:00"
  },
  "message": "Dispensing session started."
}
```

**Validation:**
| Field | Rules |
|-------|-------|
| `cup_detected` | boolean, optional |
| `hand_detected` | boolean, optional |
| `water_level_before` | 0–100 or null, optional |

**Behavior:**
- Creates row in `dispensing_sessions` with `status = started`
- Rejects if an active session already exists (HTTP 409)
- Rate limit: 30 requests per 60 seconds

---

### POST /api/device/dispensing/complete

Completes or interrupts an active dispensing session.

**Headers:** `Authorization: Bearer <token>`, `Content-Type: application/json`

**Request:**
```json
{
  "session_id": 456,
  "water_level_after": 68,
  "amount_dispensed_ml": null,
  "stop_reason": "completed"
}
```

**Response (200):**
```json
{
  "success": true,
  "data": {
    "session_id": 456,
    "status": "completed",
    "duration_seconds": 12,
    "ended_at": "2026-09-21T10:00:12+08:00"
  },
  "message": "Dispensing session completed."
}
```

**Validation:**
| Field | Rules |
|-------|-------|
| `session_id` | Required, must exist, must belong to this device, must be active |
| `water_level_after` | 0–100 or null |
| `amount_dispensed_ml` | Non-negative integer or null |
| `stop_reason` | One of: `completed`, `cup_removed`, `hand_removed`, `timeout`, `low_water`, `manual_stop`, `error` |

**Behavior:**
- Calculates duration from server timestamps
- Sets final status based on stop_reason
- Uses database transaction for consistency
- Rejects session belonging to another device (HTTP 403)
- Rate limit: 30 requests per 60 seconds

## HTTP Status Codes

| Code | Meaning |
|------|---------|
| 200 | Success |
| 201 | Created (new resource) |
| 400 | Bad request |
| 401 | Unauthorized (missing/invalid token) |
| 403 | Forbidden (device disabled, wrong device ownership) |
| 404 | Endpoint not found |
| 405 | Method not allowed |
| 409 | Conflict (duplicate active session, expired token) |
| 422 | Validation failed |
| 429 | Rate limit exceeded |
| 500 | Server error |

---

## Error Response Format

```json
{
  "success": false,
  "error": "Human-readable error message",
  "details": {
    "field_name": "Specific field error message"
  }
}
```

## Rate Limiting

| Endpoint | Limit | Window |
|----------|-------|--------|
| `heartbeat` | 30 req | 60s |
| `sensor-reading` | 60 req | 60s |
| `dispensing/start` | 30 req | 60s |
| `dispensing/complete` | 30 req | 60s |

Rate limit state is stored in temp files per device per action.

---

## Security Notes

- Raw tokens are **never stored** — only SHA-256 hashes
- Tokens are **never logged** or included in responses
- Device identity comes from the **token**, not from request body
- Revoked/expired tokens are rejected immediately
- All database queries use **prepared statements**
- API responses are always **JSON** with no PHP error leakage
- Activity logs never contain tokens, passwords, or API keys
- Wi-Fi passwords are never accepted or stored by the API
